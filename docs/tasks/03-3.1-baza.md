#### 2.8.1 Lazy enrollment — bazaga talablar (yozish 3.3 §4.1 da)
- **Qachon yaratiladi:** guruhga qo'shilganda ham, migratsiyada ham emas — student `/student/*` ga **birinchi murojaat** qilganda (odatda xaritani birinchi ochganda, `GET /student/path`). Shart: faol a'zolik bor (`group_members.left_at IS NULL`, guruh `deleted_at IS NULL`) va `groups.path_id` dagi yo'l `PUBLISHED`. Yo'l `DRAFT`/`ARCHIVED` bo'lsa enrollment yaratilmaydi (xarita `path: null`).
- **Bitta tranzaksiyada ikki idempotent yozuv** (`UnitOfWork`):
  SQL quyida **faqat semantikani tushuntiradi** (amalda Prisma generatsiya qiladi):
  ```sql
  INSERT INTO "student_path_enrollments" ("id", "student_id", "path_id", "started_at")
  VALUES ($uuid7, $studentId, $pathId, now())
  ON CONFLICT ("student_id", "path_id") DO NOTHING;

  -- zanjirning birinchi ko'rinadigan mavzusi (bo'lsa)
  INSERT INTO "topic_progress" ("student_id", "topic_id", "status", "updated_at")
  VALUES ($studentId, $firstTopicId, 'AVAILABLE', now())
  ON CONFLICT ("student_id", "topic_id") DO NOTHING;
  ```
  `id` — ilova generatsiya qilgan UUID v7 (Prisma `@default(uuid(7))`), shuning uchun PG16 da `uuidv7()` yo'qligi muammo emas (eski S-B6 o'z-o'zidan yopiladi).
- **Poyga holati:** ikki parallel birinchi so'rov (ikki tab, takroriy fetch) ikkalasi ham `INSERT` qiladi. Ikkinchisi unique indeks qulfida birinchisining commit'ini kutadi, keyin `DO NOTHING` — xato yo'q, natija bitta qator. `topic_progress` uchun xuddi shu kafolatni PK `(student_id, topic_id)` beradi. Shuning uchun:
  - **Yagona usul:** Prisma `createMany({ data, skipDuplicates: true })` (→ `ON CONFLICT DO NOTHING`). Mavjud naqsh: `apps/api/src/modules/groups/**/group-members.repository.ts:97` (`createManyAndReturn` + `skipDuplicates`). `$executeRaw` **ishlatilmaydi**: ilovada uuidv7 generator yo'q, `id` ni faqat Prisma `@default(uuid(7))` beradi.
  - **"Avval `findUnique`, yo'q bo'lsa `create`"** naqshi taqiqlanadi (poygada `P2002`/`23505`). Prisma `upsert` ham tavsiya qilinmaydi: native `ON CONFLICT` faqat ma'lum shartlarda ishlatiladi, aks holda o'qish+yozish bo'lib qoladi.
  - Tez yo'l (enrollment allaqachon bor — kesh yoki `SELECT` `uq_..._student_id_path_id` bo'yicha) yozuvsiz qaytadi.
- **Enrollment bor, birinchi mavzu qatori yo'q** holati mumkin: yo'l nashr qilingan, lekin enrollment paytida ko'rinadigan mavzu bo'lmagan; keyin mavzu nashr qilindi va tez yo'l yozuvsiz qaytdi. Baza buni taqiqlamaydi (CHECK/trigger yo'q). Backend uchun invariant: zanjirning birinchi ko'rinadigan mavzusi qatorsiz ham `AVAILABLE` hisoblanadi (3.3 §4.3 hisoblangan `AVAILABLE`), birinchi `start` uni `IN_PROGRESS` qatoriga aylantiradi.

#### 2.8.2 Yo'l almashishi
- "Joriy yo'l" bazada saqlanmaydi (`is_current`/`current_path_id` ustuni yo'q): faol a'zolik → `groups.path_id` dan har safar hisoblanadi. Shu sabab yo'l almashganda hech qanday "yangilash" yozuvi kerak emas.
- **Student boshqa yo'lli guruhga o'tsa** (chiqarish → qo'shish): yangi yo'l enrollment'i keyingi birinchi murojaatda lazy paydo bo'ladi. Eski enrollment va uning `topic_progress`/`lesson_progress` qatorlari tarix sifatida qoladi (`Restrict`, o'chirilmaydi), `completed_at` NULL bo'lib qolishi mumkin — bu "tugatilmagan, tark etilgan" degani.
- **Eski yo'lga qaytsa:** `ON CONFLICT DO NOTHING` eski enrollment'ni saqlaydi (`started_at` birinchi kirish sanasi bo'lib qoladi), progress qolgan joyidan davom etadi. Yo'l bo'yicha bitta student — bitta enrollment.
- **Guruhning o'z yo'li o'zgarishi:** hozir mumkin emas (docs/12:238 `PATCH /admin/groups/:id` da `pathId` yo'q). Kelajakda qo'shilsa ham bazaga o'zgarish kerak emas — lazy mexanizm keyingi murojaatda yangi enrollment yaratadi, eskisi tarix bo'ladi.
- **Yo'l `ARCHIVED`/`DRAFT` ga qaytarilsa:** enrollment o'chirilmaydi; resolver "yo'l yo'q" qaytaradi. Qayta nashr qilinsa — mavjud enrollment davom etadi.
- **Hisobot oqibati:** "yo'lga biriktirilgan, lekin hali kirmagan" studentlar enrollment'da yo'q — ularni `group_members` + `groups.path_id` orqali olish kerak (3.3 §4.1 "Kamchilik"). Ota-ona paneli (14-modul) uchun enrollment yo'q = 0%.

### 2.11 Migratsiyaning qo'lda yoziladigan qismi
Ish tartibi: `prisma migrate dev --create-only --name path_content_and_progress` → SQL faylni tahrirlash → `prisma migrate dev` (qo'llash). Qo'lda qism faylning oxirida, `groups_and_paths` dagi kabi sarlavha va izohlar bilan.

1. **DEFERRABLE unique** (docs/11:182, 196, 211). Prisma DEFERRABLE ni ifodalay olmaydi. Schema'da `@@unique([pathId, order], map: "uq_path_sections_path_id_order")` (va topics/lessons uchun shunga o'xshash) qoladi — Prisma Client `pathId_order` kompozit kalitini bersin. Migratsiyada Prisma generatsiya qilgan `CREATE UNIQUE INDEX "uq_..."` qatorlari **o'chiriladi** va o'rniga:
   ```sql
   ALTER TABLE "path_sections" ADD CONSTRAINT "uq_path_sections_path_id_order"
       UNIQUE ("path_id", "order") DEFERRABLE INITIALLY IMMEDIATE;
   ```
   (topics, lessons uchun ham). `INITIALLY IMMEDIATE` tanlovi: oddiy INSERT/UPDATE'da darhol xato, bitta statement ichidagi tartib almashtirish (`UPDATE ... FROM (VALUES ...)`) esa statement oxirida tekshiriladi; ko'p statementli tranzaksiyada backend `SET CONSTRAINTS ... DEFERRED` qiladi.
   **Drift tekshiruvi majburiy:** `prisma migrate diff` (1.3/2.1 dagi buyruq: migratsiyalar → schema) bo'sh chiqishi kerak. Agar Prisma constraint'ni farq deb ko'rsa yoki keyingi `migrate dev` uni qayta yaratmoqchi bo'lsa — **to'xta va hisobot ber** (zaxira varianti: DEFERRABLE'siz oddiy unique + backend ikki bosqichli tartiblash; bu docs'dan chetlanish, Tech Lead qaror qiladi).
2. **CHECK'lar:** `chk_topic_progress_status_not_locked`, `chk_topic_progress_completed_at`, `chk_lesson_progress_completed_at` (T-6 qabul qilingan).
3. **Enrollment backfill — YO'Q** (TL Q-5). Migratsiyada `student_path_enrollments` ga hech qanday `INSERT` yozilmaydi, trigger ham yo'q. Mavjud studentlar (dev'dagi `ST-10001`, 2-bosqichda guruhga qo'shilganlar) enrollment'ni lazy yo'l bilan birinchi murojaatda oladi (§2.8.1). Shu sabab UUID v4/v7 muammosi (eski S-B6) yo'qoladi: barcha `id` lar ilovada `uuid(7)` bilan yaratiladi.
